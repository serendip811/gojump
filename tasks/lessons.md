# Lessons

- 프로젝트에서 API 키 기반 기능을 만들 때는 `.env`를 Git에서 제외하는 것뿐 아니라, 런타임이 프로젝트 루트 `.env`를 실제로 자동 로드하는지 처음부터 구현하고 테스트한다.
- 상세 화면에서 원지표와 0~100 위험점수를 함께 보여줄 때 그래프의 단위와 제목을 반드시 표시한다. 원지표 추이와 위험점수 추이를 설명 없이 혼용하지 않는다.
- API 기반 UI를 변경할 때 라이브 응답만 검증하지 말고 내장 폴백과 영속 캐시도 같은 스키마로 갱신한다. 화면 검증 전에는 기존 캐시가 새 UI를 가리지 않는지 확인한다.
- 장기 시계열은 모든 관측점에 마커를 찍지 않는다. 데이터 밀도에 따라 선과 축 범위를 조절하고 최고점·최신점처럼 의미 있는 지점만 강조한다.
- K-HAI처럼 절대 수준 자체가 의미인 그래프는 선택 기간에 맞춰 축을 확대하지 않는다. Y축을 0부터 장기 공통 상한까지 고정해 기간을 바꿔도 값의 시각적 크기가 달라지지 않게 한다.
- 기간을 비교하는 차트는 선택 범위마다 Y축 최소·최대가 바뀌지 않게 공통 축을 사용한다. 실제 데이터가 없는 기간 선택지를 먼저 노출하지 않는다.
- 사용자가 가격과 거래량 시계열을 함께 주면 원천값 일치 확인에 그치지 말고, 가격의 사후 고점 라벨과 당시 위험점수를 맞춰 예측력 백테스트까지 수행한다.
- 원래 선행지표를 데이터 확보가 쉬운 후행 대체지표로 바꿀 때는 같은 의미라고 간주하지 않는다. 원 지표의 과거 데이터를 먼저 찾아 선행 시차를 백테스트하고, 대체지표는 별도 확인 신호로 분리한다.
- Swift Charts에서 복수의 `LineMark`를 한 차트에 그릴 때 색상만 바꾸지 말고 명시적인 `series` 값을 지정한다. 그렇지 않으면 첫 계열의 끝과 다음 계열의 시작이 대각선으로 연결될 수 있다. 비교선은 색상과 선 패턴을 동시에 다르게 해 작은 화면에서도 구분한다.
- JavaScript 문자열을 거쳐 Swift 코드를 패치할 때 `\\(...)` 문자열 보간의 백슬래시가 사라지지 않도록 `String.raw`를 사용하고, 빌드 성공만으로 끝내지 말고 화면에 실제 값이 렌더링됐는지 확인한다.
# UI 상태 안내

- 데이터 출처 상태와 네트워크 상태를 독립된 경고로 중복 표시하지 않는다. 실패 시 현재 화면이 캐시인지 내장 샘플인지 먼저 판별하고, 사용자가 실제로 보고 있는 데이터 상태를 하나의 문장으로 설명한다.
- 이중 축 차트의 축 제목과 최신값을 같은 모서리에 고정 배치하지 않는다. 정적 라벨은 범례로 옮기고 상세 수치는 터치 선택 시에만 표시해 축 눈금과의 충돌을 피한다.
- 이중 축의 계열 구분은 장황한 `왼쪽/오른쪽 축` 문구보다 선·범례·축 숫자의 색을 일치시키는 방식으로 먼저 해결한다.
- Swift Charts의 선택 툴팁을 `Mark.annotation`으로 만들면 가장자리에서 플롯 영역이 재배치될 수 있다. 선택 UI는 `chartOverlay`에서 플롯 좌표를 계산하고 내부로 clamp해 차트 레이아웃을 고정한다.
- 막대 값 라벨을 위해 같은 X 위치에 투명한 보조 `BarMark`를 추가하지 않는다. Charts가 막대를 그룹으로 배치해 겹침·오프셋이 생길 수 있으므로 원래 막대에 직접 annotation을 붙인다.
- 위젯 타임라인 갱신을 API 성공 분기에만 두지 않는다. 서버가 꺼진 개발·오프라인 상태에서도 새 위젯 레이아웃과 캐시가 반영되도록 앱 초기화와 실패 분기에서도 reload를 요청한다.
- 실데이터 지표를 교체하거나 폴백 경로를 추가할 때는 값뿐 아니라 `liveIndicatorCount`와 `dataMode` 전환도 함께 검증한다. 개별 변환 테스트와 전체 파이프라인의 최종 `live` 상태 테스트를 둘 다 둔다.
